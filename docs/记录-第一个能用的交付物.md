# 第一个能用的交付物

**2026-10-13。** 到这一天为止，从上游源码到「一个能开机、能装软件的系统」这条链
第一次整条走通，而且产物在公开的 URL 上。

**这是【记录】，不是【指南】。** 要查怎么构建，看 `docs/指南/`。留在这里的原因：
**这一格里程碑和之前那些不一样**——之前每一步都有产物，但没有一个「别人能拿去用」。

## 有了什么

```
两条 apk 仓库      x86_64  68 个包      aarch64  66 个包
容器镜像           base:edge · base-devel:edge
磁盘镜像           minimal-x86_64-<日期>.img.zst（48 MB）
```

磁盘镜像的稳定入口：

```
https://repo.os.yojigen.cn/img/minimal/x86_64/latest.txt
```

## 它是从哪里来的

```
上游源码 → 自举构建 → apk 仓库 → apk 装出根 → GRUB + 内核 + /init
                                    → 建盘 → QEMU 启动 → 发布
```

每一段都在 CI 里跑，而且**每一段都有自己的验收**：

| 段 | 怎么验的 |
|---|---|
| 包 | 从空容器 `apk add` 一个风味，装出来才算数 |
| 容器镜像 | 起得来 + 九个 OCI 标签齐全 |
| 磁盘镜像 | **在 QEMU 里真启动**，等它打印 `/init` 里那句「欢迎来到 Yojigen OS」 |
| 目标根能不能装软件 | chroot 进去 `apk update` + `apk add hello` + 跑 `hello` |

**最后一条是这一天补的**，因为发现了一个漏：

> 「能启动」和「能装东西」是两件事，而**前者不蕴含后者**。装根用的是【容器里的】
> apk，启动测试只看那句问候语——结果交付物里【根本没有 `/sbin/apk`】。
> 盘能起来、能 SSH，装不了任何东西。
>
> 中间没有任何一步会问「目标系统里有没有 apk」。**build-time 用的工具和交付物里
> 带的工具是两回事，而 CI 只验了前者。**

## 这一格为什么算里程碑

之前的产物都是**中间的**：包建出来了、镜像组装出来了、盘建出来了——但没有一个
「别人拿去能用」。

这一格开始有了：**一个 48 MB 的文件，从公开 URL 下载、校验值对得上、DD 到盘上
就能起，起完还能装软件。**

而它的意义不在于这个系统现在能做什么，在于**它证明那条链是活的**：

- 链上任何一段断了，最后那句话就打不出来
- 而那句话来自 `yojigen-os-init` 包里真正的 `/init`——不是 CI 里写的一句 TODO

## 一个还在的教训

这一天修了十来个东西，其中**五个是自己造的**。而共同点不是「代码写错了」，是
**「我以为我知道那一步在做什么」**：

| 我以为 | 实际 |
|---|---|
| `bash -n` 过了就没问题 | 它不是在跑的那个 shell（shebang 是 `#!/bin/sh`） |
| `sh -n` 过了就没问题 | 语法对，但少了一个命令 |
| 打印了命令就是检查了 | 打印了但没看顺序（`-v` 落在了镜像名后面） |
| 缓存存下来了 | 存的是上一轮的内容 |
| `docker run` 会带上环境 | 不会——`-e` 和 `-v` 都得显式给 |
| 修过那个坑了 | 修的是**表现**（"播种"），不是**本质**（"这个包不是本轮建的"） |

详见 `packages/docs/记录/自举历程.md` 的「四类空验证」一节。

★ 最有用的那条判据：

> **一个坑的触发条件如果钉在「某条具体路径」上，它一定会在别的路径上复发。
> 要钉在「共同的性质」上。**
