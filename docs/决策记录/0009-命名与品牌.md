## 来历

三层嵌套：

```
女孩的短裙
  └─ 四次元的空间
      └─ 四次元的系统        ← YojigenOS
```

原话：

> 四次元的系统，放在四次元的空间，四次元的空间，在女孩的短裙里面。
>
> 不能随便看，也不能随便摸，是神秘的、充满吸引力的地方。

三个名字各占一层：

| | 是哪一层 |
|---|---|
| **YojigenOS** | 四次元的**系统**——最里面那个 |
| **四次元的空间** | 装这个系统的地方 |
| **`skirt`（短裙）** | 那个空间**外面的那层**。构建工具以它命名 |

**不要往童趣的方向软化它。** 之前我把它读成「哆啦A梦的四次元口袋」，
又把「四次元空间」映射成构建容器的文件系统——两次都是替它引申，
两次都不是原意。这里记的是原话本身。

### 顺带一个技术上的呼应（这是观察，不是比喻的含义）

```
里面看不见   →  用户不需要知道构建过程
拿出来的能验  →  但可以验证产物（见 0005：冷热构建逐位一致）
```

**你看不见里面，但你能验证拿出来的东西**——一个发行版该有的样子。

## 标识符怎么拼

**这是 2026-10-12 补的一节。** 起因是一个很好的问题：`yojigenos-init` 为什么不叫
`yojigen-os-init`？

先承认一件事：**`YojigenOS` 词源上确实是两个词**——四次元 + 系统（见上面的来历，
"四次元"同时修饰空间和系统）。所以理由**不是**"它本来就是一个词"。那个说法是错的，
而且错得有害：照着它推理，下一个人会以为品牌名一律不可拆，于是遇到 `AlmaLinux`、
`Arch Linux` 这类名字时得不出规则。

真正的规则是：**词源可以是两个词，标识符里一律用闭式（closed compound）。**

| | 怎么写 | 用在哪 |
|---|---|---|
| 显示名 | `YojigenOS` | 给人看：`os-release` 的 `NAME` / `PRETTY_NAME`、文档、对外的说法 |
| 标识符 | `yojigenos` | 给机器看：`os-release` 的 `ID`、包名前缀、Docker 命名空间、产物文件名、配置路径（`/etc/yojigenos/…`） |

### 为什么不在标识符里拆

**① `-` 在标识符里有语法角色，而且已经被占满。** 看这个项目自己的包名：

```
glibc-dev      glibc-locales      dash-binsh      linux-headers
  └母包┘ └────限定词────┘
```

`-` 右边一律是"**这是母包的哪个部分**"。在这个语法里，`yojigen-os-init` 会被读成
三段（`yojigen` / `os` / `init`），读者会去找"`os` 是 `yojigen` 的什么子包"——
而那个答案不存在。

**② 复合词的标识符用闭式，是通行做法。**

| 显示名（人读的） | 标识符（机器读的） | 词源 |
|---|---|---|
| Alma**Linux** | `almalinux` | Alma + Linux |
| Arch **Linux** | `archlinux` | Arch + Linux |
| **Linux** Mint | `linuxmint` | Linux + Mint |
| open**SUSE** | `opensuse` | Open + SUSE |
| Postgres**SQL** | `postgresql` | Postgres + SQL |
| Libre**Office** | `libreoffice` | Libre + Office |

连字符在这些项目里留给**变体**，不是留给品牌内部：`opensuse-leap` 里的 `-leap`
说的是"哪个版本"，不是"品牌怎么拼"。

**③ 最漂亮的反证是 Rocky。** 它的 GitHub 组织叫 `rocky-linux`（带连字符——那是
给人读的地方），而 Docker 命名空间是 `rockylinux`（闭式）、包前缀是 `rocky-release`。
**同一家公司，一到标识符层面自己就把连字符去掉了。**

次要的一条：`yojigen` 是日语罗马字，`OS` 是英文缩写。拆开之后每个包名都要同时背
两个语种；压成一个 token，语种混合这件事只在品牌名上出现一次。

### 这条规则管到哪

- `os-release`：`NAME="YojigenOS"` / `ID=yojigenos`（现在就是这样）
- 包名：`yojigenos-init` 是**第一个**带前缀的包。后面还会有 `yojigenos-firstboot`、
  `yojigenos-release`
- Docker：命名空间是 `yojigenos`（`yojigenos/base`、`yojigenos/buildenv`）
- 产物文件名：`yojigenos-base-<架构>.tar.gz`、将来的
  `yojigenos-minimal-<日期>-<架构>.img`
- 配置路径：`/etc/yojigenos/…`（还没有，先占位）

**想要"两个词"的清晰度，位置在显示名那一层，不在标识符。** `NAME`、`PRETTY_NAME`、
README 的第一句，都有地方把"四次元系统"展开说清楚。标识符只要一个能 grep、能排序、
能当命名空间的 token。

### 已知的偏离

`var/output/aarch64/yojigen-rootfs-aarch64.tar.gz` —— 旧脚本（`rootfs.py` 那条路）
留下的产物，把 `os` 丢了。它在 `.gitignore` 范围内，不会被发布，**它不是先例**。

### 结论

**保留 `yojigenos-init`，不改名。** 2026-10-12 问过、答过，记在这里。

成本也记一笔：现在改是零成本（这个包还没打包发布，只是建出来了），发布之后因为包
仓库只增不减，就得留过渡。但改它意味着 `yojigenos/base`、Docker Hub 组织名、产物
文件名全部成为旧写法——**要改就是一次全局改名，加重建 Docker Hub 组织。**

## 目标三元组是另一类标识符

**和上一节并列，但结论相反：那里用 `yojigenos`，这里用 `yojigen`。**

三元组（`aarch64-yojigen-linux-gnu`）会出现在 gcc 的路径里、出现在
`bash --version` 的输出里、出现在 `gcc -dumpmachine` 里：

```
/usr/bin/aarch64-yojigen-linux-gnu-gcc
/usr/lib/gcc/aarch64-yojigen-linux-gnu/
/usr/include/c++/16.2.0/aarch64-yojigen-linux-gnu/
```

### 为什么它是例外

**① 它不是"品牌标识符"，是"工具链标识符"。** 上一节那张表管的是
`os-release` 的 ID、包名前缀、Docker 命名空间、产物文件名——那些说的是
**"这是哪个系统"**。三元组的 vendor 段说的是**"这套工具链出自哪里"**，
它描述的是编译器，不是发行版。两者可以不同，而且经常不同：

| | 品牌标识符 | 三元组的 vendor |
|---|---|---|
| **Fedora** | `fedora`（ID、`fedora-release`、Docker 命名空间） | `redhat` |
| **我们** | `yojigenos` | `yojigen` |

★ Fedora 是最有力的先例：它的 `os-release` 里 `ID=fedora`、包前缀一律
`fedora-`，**但 `bash --version` 说的是 `aarch64-redhat-linux-gnu`**。
同一台机器上两者并存，谁也没有取代谁。

**② 上一节的核心论据在这里不成立。** 那条规则说的是：

> `-` 在标识符里有语法角色，而且已经被占满。`glibc-dev` 会被读成
> "glibc 的 dev 部分"。

而三元组里的 `-` **本来就是分段符**——`aarch64 | yojigen | linux | gnu`
是四个字段，不是我起的一个复合词。所以在 vendor 这一段里多一个 `-`
不产生任何歧义，也不会有读者去找"`yojigen` 的哪个子包"。

**③ vendor 段的通行长度是短的。** 实测四大发行版：

```
redhat · alpine · suse · apple · pc · unknown
```

这里放的是**组织名**（`redhat` 不是 `redhatlinux`，`suse` 不是 `susesel`），
而不是产品全名。`yojigenos` 里的 `os` 在 `linux` 前面本来就是冗余的。

**④ 而且它出现在路径和文件名里。** `/usr/bin/aarch64-yojigen-linux-gnu-gcc`
每多两个字符，就在每个包的文件清单里多一次。这不是决定性的理由，但方向一致。

### 所以

| | 怎么写 | 用在哪 |
|---|---|---|
| 品牌标识符 | `yojigenos` | `os-release` 的 `ID`、包名前缀、Docker 命名空间、产物文件名、`/etc/yojigenos/…` |
| 目标三元组 | `aarch64-yojigen-linux-gnu` | gcc 的 `--host`/`--target`、它的安装路径、`gcc -dumpmachine`、`bash --version` |

**这条规则管到哪**：`skirtlib/common.py` 的 `target_triple()` 是唯一出处
（`f"{arch}-yojigen-linux-gnu"`）。驱动层给所有 autotools 包无条件加
`--host=`，gcc 在它自己的 `steps.sh` 里加 `--host`/`--target`。
配方不该自己拼这个字符串。

★ 实测 `config.sub` 原样接受它（aarch64 和 x86_64 都被接受，不会被归一化），
所以它是个合法的三元组，不是自造格式。

## 对外怎么说，是另一件事

这不影响上面那个意象的成立，但它是个实际要面对的问题：

- 命令名 `skirt` 是英文，字面含义中性
- 中文那层意思，只有懂的人懂
- 但**如果将来面向更大的受众**（英文用户、企业、机构），这层意象要不要另做
  一层解释——**没想，也不急。**

## 版本代号

想用**二次元美少女的名字**给版本起别称。三个方向：

| 选项 | 风险 | 二次元浓度 | 说明 |
|---|---|---|---|
| 直接用动漫角色名 | 低 | 满 | 先例充足，但名字不属于我们 |
| **日本神话 / 传说** | **零** | **很足** | 公有领域。**而且动漫本来就大量取材于此**——对受众来说一样「很二次元」，却没借任何人的 IP |
| 原创少女名 | 零 | 取决于起得如何 | 完全属于我们，能形成自己的谱系 |

### 关于风险的分寸

涉及的是**商标**，不是版权。

- **版权**：角色**名字**本身一般不受版权保护（版权保护表达，不保护名字）
- **商标**：但角色名**可以**被注册（例如「初音ミク」是 Crypton 的注册商标）

**Debian 的先例**：从 1996 年起用《玩具总动员》的角色名做代号，从没申请过授权，
Pixar/迪士尼也从没追究。但要注意他们的分寸——**只用名字**，不用角色形象、不用
原画、不用字体、不拿它当产品名。代号是技术性的，不是招牌。

**风险等级**：非商业开源项目、只用作代号、不涉图像 → 低。但只要沾上捐赠或商业
活动，就往上走一格。

**倾向第二个方向**（神话）：神话名字之所以「二次元」，正是因为动漫一直在用它们。
所以天照、月読、玉藻、不知火、雪女这类名字，读者看到会自动代入那个气质——
**而没有人能来说这是他的。**

## 补记：显示名改成 `Yojigen OS`（2026-10-12 晚）

上面那张表里写的是「显示名 `YojigenOS`」。**那一格后来改了，现在是 `Yojigen OS`。**

### 为什么

用户的原话是：

> 显示名，我希望可以是 **Yojigen OS**，因为 Yojigen 和 OS 是两个词。

也就是说上面那个区分被推到了它该在的位置：

| | 怎么写 | 理由 |
|---|---|---|
| **显示名** | `Yojigen OS` | **它确实是两个词，就该让两个词都看得见** |
| **标识符** | `yojigenos` | 闭式，对齐 Docker 命名空间（见下） |

### 这一条不改上面那条规则，它把那条规则说清楚了

上面论证的是「**标识符**里不拆」——因为 `-` 在包名里有语法角色、因为复合词标识符
通行用闭式。**它从来没有论证过显示名要连写。** 当时把显示名也写成闭式，是顺手
跟着标识符走的，没有独立理由。

所以这次不是推翻，是补上缺的那一半：**能拆的地方（给人读的）就拆，不能拆的地方
（给机器读的）才连写。**

### 标识符一律不动，而且这次不是偏好问题

Docker Hub 的**命名空间不允许连字符**（只允许小写字母和数字，4~30 字符）。所以

```
yojigenos/base          只能这样，不是选择
yojigenos/base-devel
```

而组织转过去之后**命名空间不能改名**。于是标识符这边没有第二个选项——包名前缀
`yojigenos-` 跟着 Docker 命名空间走，比跟着显示名走更省事，也少一处需要解释的
不一致。

### 这次实际动了什么

```
改    os-release 的 NAME / PRETTY_NAME
      /init 的欢迎语
      仓库描述（repo.sh 的 --desc）、启动菜单项、文档正文
不改  ID=yojigenos · LOGO=yojigenos · 包名前缀 yojigenos-
      github.com/YojigenOS（组织名，改了链接全断）
      docs/记录/（历史日志记的是当时发生了什么）
      docs/决策记录/0016 与本文上面的部分（不可变——所以是追加，不是改写）
```

`filesystem` 因此 bump 到 release 2：它的 `/etc/os-release` 变了，而那个文件在
产物里。

### 判据（下次遇到类似的名字时用）

**问一句就够了：这个字符串是给人读的，还是给机器读的？**

- 给人读的 → 按自然写法来（该有空格就有空格）
- 给机器读的 → 对齐它所在的那个生态的硬约束（Docker 不许连字符、`-` 在包名里
  是子包语法）
