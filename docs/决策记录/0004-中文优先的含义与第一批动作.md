# 0004 中文优先的含义与第一批动作

- **日期**：2026-10-10
- **状态**：已决定（边界由 [0012](0012-中文优先的边界.md) 厘清；apk 部分已由 [0006](0006-包管理器选型与中文支持.md) 结掉）
- **影响范围**：所有配方的 `configure` 参数、glibc 的安装步骤、将来包管理器的选型

## 背景

"中文优先"从项目第一天就是三条需求之一，但一直**没有具体定义**。更糟的是，
我们在**反向操作**：

```toml
configure = ["--prefix=/usr", "--disable-nls"]
```

`NLS` = Native Language Support。这个参数被加进了 bash、coreutils、sed、grep、
gawk、tar、findutils、diffutils、gzip、xz 的配方——**所有的基础命令都不安装
翻译**。当初加它是为了少一个构建依赖（gettext），那时项目还没有"中文优先"的
意识。**结果是一个中文优先的系统，系统消息全是英文。**

另外，glibc 的 `zh_CN.UTF-8` locale 数据很可能根本没生成——`make install`
不包含 locale 生成，要单独跑。

## 决定

### 一、"中文优先"= 默认的中文环境

明确定义为：**系统的默认语言环境、提示信息、帮助文本、文档以中文为主。**

它**不是**"开箱能跑微信、WPS"——那是兼容性问题（需求 2），是另一件事。把两者
分开，这一条才可衡量、可完成。

### 二、"优先"是排序，不是排他

**中文第一，英文可用，不把任何人挡在外面。** 这条原则同时约束将来的文档、
社区和发布策略。

### 三、第一批动作（不需要 fork 的部分）

1. **去掉所有配方里的 `--disable-nls`**，并给需要的包加上 `gettext` 构建依赖。
2. **glibc 生成 locale 数据**（至少 `zh_CN.UTF-8`、`en_US.UTF-8`）。
3. 这两件事都会让产物字节变化，**需要在同一次重建里做完**（和 strip 那批一起）。

代价是**每个包都要重建一次**，但这是最后一次因为中文而重建。

### 四、apk 的评估顺序：先做 90%，再决定

实测（2026-10-10）：

| 包管理器 | 中文 | 证据 |
|---|---|---|
| apt / dpkg | ✅ | deb 包内含 `apt.mo`、`dpkg.mo` |
| pacman | ✅ | libalpm / scripts / src 三个翻译域都有 `zh_CN.po` |
| **apk**（Alpine） | ❌ | `/sbin/apk` 与 `libapk.so` **零个 gettext 符号**，包内零 `.mo` 文件 |

而 Alpine 给别的软件都发了 `-lang` 语言包——**唯独 apk 自己没有**。这不是疏忽，
是设计：i18n 要拖进 gettext，与 Alpine 的体积目标冲突，**上游大概率不会接受**。

**决定：不死磕。先把不需要 fork 的部分做完，再回头评估 apk。**

理由是判断的准确性：**"apk 说英文有多难受"，在一个周围全是英文的系统里问，
和在周围全是中文的系统里问，答案不一样。** 现在它刺眼，是因为别的东西也没中文
（是我们自己关掉的）。等基础命令都说中文了，再决定要不要为包管理器打补丁。

## 补丁方案（待评估，尚未实施）

如果届时决定给 apk 加中文，用**窄补丁**：

apk 的消息都经过几个集中的输出函数（`apk_message`、`apk_error`、`apk_warning`）。
**只改这几个函数**：把格式串拿去查表，命中就打印中文格式串配同样的参数，未命中
就原样打印英文。

| | 宽补丁（改每个字符串字面量） | **窄补丁（只改输出函数）** |
|---|---|---|
| 触及范围 | 几百个调用点 | 3~4 个函数 |
| 上游改了消息文本 | **冲突，构建失败** | **不冲突** |
| 后果 | 得去 rebase | **那条消息退回英文** |
| 失败方式 | 响亮但麻烦 | **优雅降级** |

"退回英文"是可以接受的失败：不崩、不错乱，只是那一条没翻译。而 `--fuzz=0`
兜着底——补丁不精确匹配时构建直接失败，不会"差不多"地贴上去。

## 后果

- 所有包需要重建一次（和 strip 一起做）。
- 将来加新包时，**默认不加 `--disable-nls`**。
- 系统体积会变大一些（翻译文件、locale 数据）。这是"中文优先"应有的成本。
- 文档和社区运营同样适用"中文优先，英文可用"。

## 未采用

- **把"中文优先"理解为"能跑国产软件"**：那是需求 2（兼容性），混在一起两件事
  都做不好。
- **现在就决定 fork apk**：在周围还是英文环境时做这个判断，依据不足。
- **用 gettext 给 apk 做 i18n**：gettext 是重家伙（.mo 格式、locale 解析、
  libintl）。apk 需要的只是"把几百条字符串按语言换掉"，一个查表函数足够。
