# 0001 库路径布局：统一使用 `/usr/lib`

- **日期**：2026-10-10
- **状态**：已决定
- **影响范围**：所有包的文件布局；运行时动态链接搜索路径

## 背景

项目最初定下的技术选型里，有一条没有展开：**库放在哪个目录**。当时只写了"朴素 `/usr/lib`，不用 multiarch"，但那是在还没有任何包遵循它的时候写下的。

这个决定在构建 gcc 时被逼出来了。gcc 默认把目标库（libstdc++、libgcc_s、libatomic 等）装进 **`/usr/lib64`**：

```
/usr/lib64/libstdc++.so.6 -> libstdc++.so.6.0.36
```

而其他包走 autotools 默认（`$prefix/lib`），都在 `/usr/lib`：

```
/usr/lib/libz.so.1.3.2
/usr/lib/libgmp.so.10
/usr/lib/libmpfr.so.6
/usr/lib/libmpc.so.3
```

**同一个系统里出现两个库目录，且没有一处显式规定过。**

## 问题

这不只是"不好看"。它会让验证变成假的：

在 Debian 宿主上做 C++ 验证时，`g++` 链接用的是我们的 libstdc++（6.0.36），但运行时动态链接器找不到 `/usr/lib64`（Debian aarch64 的默认搜索路径是 `/lib/aarch64-linux-gnu`、`/usr/lib/aarch64-linux-gnu`、`/lib`、`/usr/lib`），于是加载了 Debian 的 libstdc++（6.0.33）。

**程序跑起来了，用的却不是我们的库。** 这类"验证通过但验证错了"的失败，比直接报错危险得多。

## 决定

**统一使用 `/usr/lib`，不使用 `/usr/lib64`，也不使用 multiarch 子目录。**

其他包无需改动——autotools 默认的 `$prefix/lib` 就是它。gcc 是唯一例外，纠偏方式见「实施」。

## 理由

| | `/usr/lib` | `/usr/lib64` | multiarch（Debian 式） |
|---|---|---|---|
| 存在理由 | 通用 | x86 上 32/64 位共存的历史产物 | 同机多架构并存 |
| 对 aarch64 纯 64 位 | 概念干净 | 无意义 | 过度设计 |
| 是否在默认搜索路径 | **所有 Linux 都含它** | 需额外配置 | 需额外配置 |
| 已有包现状 | **已在这** | 要全改 | 要全改 |

三条理由按重要性排序：

1. **一致性**。布局必须被所有包遵守。允许例外，就等于允许"运行时悄悄加载到宿主的库"。
2. **默认搜索路径**。`/usr/lib` 在任何 Linux 上都是默认搜索路径之一，`/usr/lib64` 不是。少一处需要自己配置的地方。
3. **概念对应**。lib64 的存在是为了解决 32/64 位共存，而本项目明确单架构、`--disable-multilib`，这个问题不存在。

## 实施：gcc 这个例外怎么处理

这条决定在构建 gcc 时遇到第一个挑战，过程值得记述。

**第一次尝试（失败）**：给 gcc 传 `--libdir=/usr/lib`。

顶层 `libdir` 确实变成了 `/usr/lib`，但 libstdc++ 仍然装进了 `/usr/lib64`。原因是目标库不走顶层 `libdir`：

```
libstdc++-v3/Makefile:
  toolexeclibdir = $(glibcxx_toolexeclibdir)
  glibcxx_toolexeclibdir = ${libdir}/../lib64
```

而那个 `../lib64` 源自 gcc 的 aarch64 目标配置，是写死的：

```
gcc/config/aarch64/t-aarch64-linux:
  MULTILIB_OSDIRNAMES = mabi.lp64=../lib64...
```

**最终方案**：在 `package()` 里、安装之前，把 `$PKGDEST/usr/lib64` 做成指向 `lib` 的符号链接。

效果：gcc 的安装路径不变（它照旧往 `/usr/lib64` 装），但文件实际落进 `/usr/lib`；`/usr/lib64` 保留为链接，使运行时与已写入的路径仍然可解析。

不选打补丁，是因为补丁要长期维护（每次 gcc 升级都得重打），而符号链接是一次性的、且不改变上游行为。

**技术债**：这个链接目前由 gcc 包携带，它本该属于一个 base-files 之类的包。将来建立该包时应挪过去。

## 后果

- 库文件路径单一：`/usr/lib/libfoo.so.*`
- `/usr/lib64` 存在，但它是指向 `lib` 的符号链接，**不是第二个库目录**
- **未来每个包都必须遵守这条**。若有包默认装到别处，必须在配方里显式纠偏，不能放任——gcc 的 lib64 就是这么处理的
- 将来构建自己的 glibc 时，其默认动态链接器搜索路径应包含 `/usr/lib`
- 验证自建产物时，仍需 `LD_LIBRARY_PATH=/usr/lib` 以压过宿主 Debian 的 multiarch 路径——**这个临时措施在自举完成、不再借用 Debian 之后即可取消**

## 未采用

- **`/usr/lib64`**：接受 gcc 默认、其余包加 `--libdir` 纠偏。放弃原因：lib64 对本项目无概念收益，却要改动更多包。
- **multiarch（`/usr/lib/<triplet>/`）**：放弃原因：一次只为一个架构构建，不需要同机多架构共存；且每个包、每个构建系统都要处理 triplet，复杂度不划算。
