## 背景

自举完成后，我们构建出的根文件系统会成为可分发的基础镜像，桌面等变体从它派生。
这件事必须**在发布之前**定下来：镜像名一旦公开就很难改——用户的 Dockerfile 里
写死了 `FROM`，改一次就是一次破坏性变更。

同时发现驱动里已经埋了一个问题。现在是：

```python
BUILDENV_IMAGE = "yojigenos/buildenv"   # 本地开发用，tag 带架构
```

本地开发这样很直观（两套工具链分得清清楚楚），但对发布是错的：

```bash
docker pull yojigenos/buildenv      # ❌ 没有 latest，拉不到任何东西
```

## 决定

### 仓库名放变体，tag 放版本

```
yojigenos/base          最小运行时（glibc + shell + coreutils）
yojigenos/base-devel    base + 工具链与构建工具    ← 自举容器，skirt 用它
yojigenos/desktop       base + 桌面环境

tag = 版本：:latest、:0.1.0、:2026.10
```

### 架构用多架构清单，不进 tag

本地开发保留 `:aarch64` 这类直白 tag。**发布时**用 buildx 合成清单：

```
yojigenos/base-devel:latest              ← 清单，用户只认这个
  ├── linux/arm64  →  :latest-arm64
  └── linux/amd64  →  :latest-amd64
```

用户写 `FROM yojigenos/base-devel:latest`，Docker 按平台自动选。

## 理由

**变体为什么占仓库名而不是 tag。** 我们的变体之间差一个数量级的体积、用途也完全
不同：`base` 几十 MB，是给人当 `FROM` 用的；`desktop` 上 GB，是给人用的。它们是
**不同的产品**，不是同一个产品的口味。tag 应该只留给"版本"这一个维度——变体 ×
版本塞进同一个 tag 会变成 `0.1.0-desktop-slim` 这种组合爆炸。

**为什么叫 `base-devel` 而不是 `buildenv`。** `base-devel` 自己说明了它和 base 的
关系（Arch 的惯例）；`buildenv` 说不清。对外的名字要能让没用过这个项目的人读懂。

**架构为什么不能进发布 tag。** 这是 Docker 的模型：一个 tag = 一个清单 = 多个平台。
把架构写进 tag 会破坏 `docker pull` 的平台自动选择，也强迫用户必须知道自己是
什么架构——而绝大多数人不需要知道。

## 后果

- `tools/skirtlib/common.py` 里的 `BUILDENV_IMAGE` **暂不改名**。本地开发继续用
  架构 tag；对外发布时另建 `yojigenos/base-devel`。两者可以并存，也可以用改名
  统一，代价只是一行常量。

  这里有个漂亮的收尾值得保留：自举完成时，`tools/buildenv/Dockerfile` 的
  `FROM debian:stable-slim` 会换成 `FROM scratch` + 我们自己的 rootfs，
  **文件名不用改、tag 不用改，构建环境的身份没变，只是内容从借来的变成了自己的。**

- 首次发布前必须把 buildx 的多架构流程配好，否则用户拉不到东西。
- **桌面镜像与容器镜像的关系需要在发布时想清楚**：桌面发行版通常是 ISO 而不是
  容器（需要显示服务、GPU、硬件适配）。`yojigenos/desktop` 若要作为容器存在，
  它更接近 linuxserver.io 的 webtop 那类"在浏览器里访问的桌面"，而不是一个可安装
  的系统。这是两个不同的东西，别让名字把它们混为一谈。

## 标签方案

### `latest` = 推荐使用的那个（不是"稳定"）

这条比"latest = 稳定"更准确，因为它同时解释了固定和滚动两种发行版的行为：

| 发行模式 | 推荐使用的是 | `latest` 指向 |
|---|---|---|
| 固定发行 | 稳定版 | stable |
| 滚动发行 | 当前滚动版 | rolling（Arch 就是这样） |

反面例子同样说明问题：**预发布版本永远不占用 `latest`**——`node:22-rc`、
`python:3.14-rc` 都用自己的 tag。

**我们现在没有"推荐使用"的东西**：构建是"配方写成什么样就构建成什么样，谁改了
谁重建"，它是开发快照，不是稳定版，甚至也不是一个有意为之的滚动版。**在这种情况下
占着 `latest` 是对用户撒谎。**

### 现在用 `edge` + 日期快照

```
yojigenos/base-devel:edge          开发通道的最新构建（移动）
yojigenos/base-devel:2026.10.10    那天的那张，永远不变
```

**通道为什么叫 `edge` 而不是 `latest-devel`。** `devel` 会和仓库名 `base-devel`
里的 `devel` 撞意思——后者指"有构建工具"，前者指"开发通道"。同一个词在同一个
tag 里出现两次、意思是两回事，读的人得猜。通道归通道，内容归内容：

```
仓库名  base-devel   →  这是什么（有构建工具的底座）
tag     edge         →  这是哪个通道（开发前沿）
```

（`edge` 也是通行叫法，Alpine 的 `alpine:edge` 就在这个位置。）

### `edge` 什么时候移动

**跟着"有意义的变化"走，不定时。** 自举跑通、工具链换代、有新能力可用——这些是
发版。每次 CI 跑完就推一个不是。

这条原则贯穿整个标签方案：**发版是一个动作，不是一个副作用。** 日期 tag 同理——
只在有意义的节点发，不是每次重建都发，否则 tag 会退化成流水账，"这版是什么"
这个信息就没了。

### 元数据进 LABEL，不进 tag

```dockerfile
LABEL org.yojigenos.recipe-commit="b3833bc"
LABEL org.yojigenos.built="2026-10-10T15:30:00Z"
LABEL org.yojigenos.packages="filesystem glibc bash coreutils …"
```

**tag 是接口，LABEL 是注释**：接口改了就破坏用户，注释随时能加。所以拿不准该不该
进 tag 的东西（时间戳、git sha、包清单）一律放 LABEL。

### 精确性靠 digest，不靠版本号

```
docker pull yojigenos/base-devel:edge             # 我大概要当前的
docker pull yojigenos/base-devel@sha256:abc123…   # 我就要这一个，永远
```

Docker 本来就提供 digest。**所以 tag 只需要为「人」服务**，精确复现不用它操心。
这是"现在不急着定版本号"能成立的底气。

## 未采用

- **一个仓库 + 变体做 tag**（`yojigenos/os:desktop`）：变体和版本两个维度会撞车。
- **架构继续留在发布 tag 里**（`yojigenos/base:aarch64`）：破坏平台自动选择。
- **用 `latest` 指向开发快照**：占用了一个承诺位置却没有承诺。
- **通道叫 `latest-devel`**：`devel` 一词两义，和仓库名撞车。
- **用语义化版本号（0.1.0）**：在没有东西可支持之前写版本号是编造承诺。
  等第一个发布出现时再加，届时 `latest` 和 `0.x.0` 一起出现。

## 补记：标签的命名空间换成真域名，并补上 OCI 标准组（2026-10-13）

上面写的三个标签是：

```dockerfile
LABEL org.yojigenos.recipe-commit="b3833bc"
LABEL org.yojigenos.built="2026-10-10T15:30:00Z"
LABEL org.yojigenos.packages="filesystem glibc bash coreutils …"
```

**「元数据进 LABEL，不进 tag」这一条没变，也依然对。** 变的是命名空间和具体字段。

### 一、`org.yojigenos.` 声明了一个我们并不拥有的域名

标签的命名约定是**反写域名**：

```
org.opencontainers.image.source     →  opencontainers.org
com.example.mykey                   →  example.com
org.yojigenos.flavor                →  yojigenos.org   ← 不是我们的
```

我们拥有的是 **`yojigen.cn`**，所以根应该是 `cn.yojigen`：

```
cn.yojigen.os.flavor
cn.yojigen.os.arch
cn.yojigen.os.built
```

★ 这一层比「连字符怎么写」重要得多。`org.yojigenos` 和 `org.yojigen-os` **都合法、
都能用**——但两个都指向一个不存在的域名。**合法不等于对。** 反写域名的全部意义
就是"这个键归谁管"，写一个不拥有的域名等于把这个意义丢掉了。

### 二、补上 OCI 标准组

原文那三个是我们自己发明的字段。OCI 有一组**标准标签**，工具真的会读它们
（`docker inspect`、镜像扫描器、供应链工具）——写了别人就能知道这个镜像从哪来：

```
org.opencontainers.image.title        Yojigen OS base
org.opencontainers.image.version      edge
org.opencontainers.image.created      2026-10-13T02:23:40Z
org.opencontainers.image.source       https://github.com/YojigenOS/distro
org.opencontainers.image.url          https://os.yojigen.cn
org.opencontainers.image.revision     69e61928cf98…      ← 对应原文的 recipe-commit
```

**原文的 `recipe-commit` 用标准的 `revision` 就够了**，不必自己再造一个。
`built` 同理——它和 `created` 是同一件事，保留 `cn.yojigen.os.built` 只是为了
自己人看着顺。

`packages` 这一个**还没做**：包清单在镜像里的 `/etc/yojigen-os-manifest`，
`docker import` 的时候还没解出来。想要的话得在组装前从 tar 里读一次。
先记着。

### 三、一个坑

`docker import -c "LABEL …"` 会**按空格切**。值里有空格就必须加引号：

```sh
-c "LABEL org.opencontainers.image.title=\"Yojigen OS base\""     # ✓
-c "LABEL org.opencontainers.image.title=Yojigen OS base"          # ✗
```

不加报的是：

```
Error response from daemon: Syntax error - can't find = in "OS"
```

——只提到 `OS`，看不出是 `title` 那一行出的问题。

### 四、验在哪儿

`scripts/verify.sh` 会检查这七个标签**存在且非空**（不检查具体值——时间戳和
commit 每次都不同）。判据是「计划了但没写进去」和「写了但写错」对外面的人
一样糟：都看不出区别。
