# 0012 中文优先的边界

- **日期**：2026-10-10
- **状态**：**已决定**
- **影响范围**：所有配方的 `configure` 参数、`LINGUAS` 的处理、apk 的中文补丁（0006）

## 背景

决策记录 0004 说「中文优先」，但没有说清楚**优先到什么程度、边界在哪**。讨论
man page 中文化的时候，这个问题浮出来了：

```
第 2/3/5 节（~30 个，集中在少数项目）  →  有中文翻译项目可以借
第 1 节（186 个，散在 15 个上游）      →  要分别去说服每个上游，而且会一直腐烂
```

**如果"中文优先"意味着"把所有英文文档翻成中文"，那就是一个永远不会完成的工程。**

## 决定

### 一、政策：有中文的，就用中文；没有的，不强求

```
上游做了中文     →  装它、让它生效 ✓
上游没做中文     →  不自己翻译 ✗
```

**关键区别：这件事不是"把中文加进去"，是"别把已有的中文丢掉"。**

后者便宜得多，而且是可完成的。

对我们的 23 个包来说，**已经做到了**：

```
zh_CN 的 .mo   12 个   ← glibc bash coreutils sed grep gawk
zh_TW 的 .mo   11 个     findutils diffutils tar gettext
```

没有的那 13 个（`gcc`、`binutils`、`make`、`gzip`、`xz`、`zlib`…）**上游本来
就没做**，我们也不该自己上。

### 二、于是它变成每个新包过一遍的三条检查

```
1. 上游有没有中文资源？               → 有就装 ✓
2. configure 有没有关掉 NLS？          → --disable-nls 是禁止的 ✗
3. 有没有用 LINGUAS 之类裁过语言？      → 裁了就必须包含 zh_CN
```

第 2 条已经做到了：今天从 15 个配方里删掉了 `--disable-nls`。

**第 3 条是陷阱。** `LINGUAS` 优化（待办 6.10）能砍掉 337 个 `.mo` 里的大部分，
但设错了会把中文也砍掉。而且它有个已知问题：有些包会因为 `LINGUAS` 里列了它
没有的语言而构建失败——这也是当初缓做它的原因。

### 三、例外：apk

**apk-tools 上游不接受中文，而我们想要它。** 所以这是一个**明确的、唯一的例外**。

三点说清楚：

| | |
|---|---|
| **它不是贡献** | 本来想过「做完提给上游，Alpine 也用上」——**这条路不通**，上游不要 |
| **它是我们长期的补丁** | apk-tools 每次更新，我们都要重新 rebase ✗ 这是一笔持续的维护成本 |
| **现在搁置** | 不取消，但也**不排在前面**。等 `minimal` 真的能用、真的有人用的时候再说 |

（这也解释了为什么 0004 里那句「apk 部分待评估」当时结不掉——它不是技术问题，
是**政策要有例外**。）

## 为什么这个政策是对的

**不是"能少做就少做"，而是它把目标定在可完成的地方。**

- 翻译别人的 man page：十万行起，而且永远在腐烂 ✗
- 保证上游做的中文都被用上：**有限的、可检查的、能做完的** ✓

而且第二件事**才真正对用户有影响**：一个中国用户 `ls` 打错了，看到的是
「无法访问」，而不是 `cannot access`——因为 coreutils 上游做了这件事，我们做的
只是**没有把它关掉**。
