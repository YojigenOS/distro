## 背景

下一个里程碑是「**真实运行**」——把系统启动起来。而在这之前，我们其实**没有
"使用"一个系统的手段**：

```
现在：docker run（不是真系统，共用宿主内核）
将来：qemu -nographic（真系统，但只有串口控制台）
```

**串口控制台只能"看"，不能"驱动"：**

| | 串口控制台 | SSH |
|---|---|---|
| 跑一条命令 | 人工敲、人工读回显 | `ssh root@vm '命令'` |
| 传文件 | 几乎没法传 | `scp` / `rsync` |
| 多路会话 | ❌ | ✅ |
| 端口转发（测 web 服务） | ❌ | ✅ |
| **脚本化** | ❌ | ✅ |

最后一行是关键。**有没有 SSH，决定了虚拟机是"盯着看的窗口"还是"能驱动的机器"。**
后者才谈得上端到端的自动化测试——而这个项目后面每一步都要靠它。

对 AI 协作来说这一点更突出：控制台要人读回显，SSH 让命令可以被程序驱动。

## 决定

### 一、可启动的镜像默认带 openssh

```
容器风味       docker exec 就够了，不加 sshd
可启动风味     SSH 是唯一的远程方式，加
```

**这是决策记录 0007 那个两维度模型第一次派上用场**：同一个风味（`minimal`），
容器版不需要 SSH，ISO 版需要。

### 二、成本几乎为零

```
openssl   →  已经在关键路径上（curl 和 apk 都要它）
shadow    →  已经在 base 的清单里（useradd、passwd）
zlib      →  已经有了
openssh   →  只多这一个配方
```

**给可启动镜像加 SSH，代价是一份配方。**

### 三、开发时只用密钥认证

不设密码，端口只转发到 localhost。开发用够了。

（**生产镜像不该是这样**：`server` 风味应该默认禁止 root 直接登录。开发和发布
是两套配置，这一点在实现时要分开。）

### 四、`scripts/run-vm.sh` 承担这件事

```bash
scripts/run-vm.sh minimal &                  # 后台起 QEMU，转发 2222 → 22
ssh -p 2222 root@localhost 'uname -a'        # 直接跑命令
scp 某文件 root@localhost:/tmp/               # 传文件
ssh -p 2222 root@localhost 'apk add nginx'   # 在真系统里装东西
```

脚本负责：起 QEMU、转发端口、**提示怎么连**。

## 还没定

### 1. 密钥怎么进去

| 方案 | 好处 | 问题 |
|---|---|---|
| 预置在镜像里 | 最简单 | 发布出去的镜像里带着一个开发私钥对应的公钥 ✗ |
| `run-vm.sh` 生成并注入 | 干净 | 需要一种注入机制（seed 盘？`-fw_cfg`？） |
| 首次启动走串口设密码 | 零机制 | 每次都要人工操作，破坏脚本化 ✗ |

**倾向第二种，但机制没想好。** 也可能开发构建和发布构建本来就该分开，
那样第一种就够了。

### 2. 主机密钥什么时候生成

标准做法是首次启动时生成 ✓ 但那需要 `ssh-keygen` 在系统里，而且首次启动会慢几秒。
**没想。**

### 3. 要不要顺带把 rsync 也加进去

`scp` 够用，`rsync` 更省事但多一个包。**没想。**
