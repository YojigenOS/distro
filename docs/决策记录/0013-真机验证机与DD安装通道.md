# 0013 真机验证机与 DD 安装通道

- **日期**：2026-10-10
- **状态**：**已决定**（2026-10-12 补齐：产出方式、托管位置、引导器选型，见第六节）
- **影响范围**：交付形式模型（0007）、`skirt` 的产物类型、将来的镜像构建、真机验证机（TX）的用途

## 背景

一台服务器到手了（腾讯云 CVM，SSH 别名 `TX`）。问题是：**怎么把我们自己的系统装上去？**

自然的想法是找现成的重装脚本，比如 <https://github.com/bin456789/reinstall>。
它确实能用，但它的五个功能里**只有一个**能接自建发行版。而搞清楚是哪一个，
顺手把几件悬着的事定了。

## 一、那类工具不是安装器

| 功能 | 命令 | 对我们的意义 |
|---|---|---|
| 重装到 20 种常见发行版 | `reinstall.sh debian 13` | ❌ 它认识的是别人家的镜像源 |
| **DD RAW 镜像到硬盘** | `reinstall.sh dd --img URL` | ✅ **唯一入口** |
| 引导到 Alpine Live OS | `reinstall.sh alpine --hold 1` | 🔧 救援与手动操作 |
| 引导到 netboot.xyz | `reinstall.sh netboot.xyz` | 🔧 同上 |
| 装 Windows ISO | `reinstall.sh windows` | ❌ |

它的工作方式是**先把自己引导进一个临时的 Linux 内存环境，再从那里装系统或写盘**。
所以它不是安装器，是「**引导 + 写盘**」。

功能 1 之所以能装 20 种系统，是因为它内置了那 20 种系统的无人值守流程——
对我们这种它没听说过的系统，这条路不存在。

**DD 那条路支持什么：**

```
raw 和固定大小的 vhd
未压缩，或压缩成 .gz .xz .zst .tar .tar.gz .tar.xz .tar.zst
```

正好是发布附件的形状（0007 已经定了可启动产物进 Releases）。

**最要紧的一句话在它的文档里：**

> DD Linux 镜像时，**不会**修改镜像的任何内容。

对 DD Windows 它会自动扩展系统盘，静态 IP 的机器还会配好 IP；对 Linux
**什么都不做**。这句话决定了后面所有的设计——**镜像得自己带一切。**

有一个例外接口：`--cloud-data`，可以给 DD 的 Linux 镜像注入 cloud-init 的
NoCloud 配置（`user-data` 必需，`meta-data` / `network-config` 可选）。但那是
**外部的可选注入**，不能当作我们的配置机制。

两条备用路径：`--hold 1` 只重启到安装环境不安装（先验证网络），`--hold 2`
DD 完不重启（SSH 进去改）。救砖则是进环境后跑 `/trans.sh alpine`。

> ⚠️ 它不支持 OpenVZ / LXC 容器型 VPS。TX 是 KVM，不在这个限制里。

## 二、决定：磁盘镜像是独立的交付形式

**0007 待定项 #4 的答案：该分开。**

0007 开头列了四种形式（容器 / ISO / 磁盘 / 内核），但下面的矩阵只画了两列。
**本记录填的是「磁盘」这一格。**

分开的理由**不是格式，是消费方式**：

| | ISO | `.img` |
|---|---|---|
| 分区表 | 不需要 | 必须有 |
| 引导器写在哪 | 挂载方决定 | 构建时写死 |
| 里面是什么 | 只读压缩 + 可写层 | 解开就是系统本身 |
| 首次启动配置 | 安装器负责 | 镜像自己负责 |
| **谁能用** | 有 IPMI / VNC / U 盘的人 | **只有 SSH 的人** |

最后一行是决定性的。**`.img` 是唯一一种对方不需要认识我们的形式。**

netboot / kexec 那条路技术上也能无人值守——reinstall 的功能 3 就是——但它要求
**对方的引导器里得有我们这一项**，而 reinstall 的菜单里只有那 20 种。DD 不同：
它是一次通用的「把这些字节写进硬盘」，**不需要任何人的配合**。

## 三、决定：VPS 这条路径上，我们不写安装器

README 的「现在不要做的事」里写着**安装器**。这条决定把它从清单里划掉：

**不是推迟，是取消**——至少在 VPS / 服务器这条路径上。

代价换成了一条义务：**产出 `.img`，并且它自带一切。** 引导链、内核、`/init`、
首次启动配置，Docker 里能跑通的东西一样都不能少。

（真机从 U 盘装、要人参与选分区的那种安装器是另一件事，这里没有取消它。
但它也不是现在的事。）

## 四、实测出来的约束

下面每一条都是从 TX 上量出来的，不是推测。实现 `.img` 的时候直接照这个来。

```
x86_64   Xeon Platinum 8255C @ 2.50GHz   4 vCPU
3.6 GiB 内存        40 GiB 盘（vda，virtio-blk）
Rocky Linux 10.2    kernel 6.12          腾讯云 CVM，KVM
```

### 引导：BIOS + GPT，而模板留了双引导的位置

```
vda1   512M   EFI System      ← 存在，但没被使用
vda2     1M   BIOS boot       ← 现在走的是这个
vda3  39.5G   Linux root      ← xfs
```

`/sys/firmware/efi` 不存在，所以是 SeaBIOS 引导；1M 的 `vda2` 正是 GPT 下
grub-pc 需要的 `bios_grub` 分区。而 ESP 也在——**腾讯云这套模板是双引导布局。**

因为 DD 一个字节都不改，**镜像自己的分区表就是最终分区表**。所以我们的 `.img`
也应该做成混合 GPT（`bios_grub` + ESP 都在），否则换一台同商家的实例可能起不来。

### 网络：NAT 内网 + DHCP，不用硬编码

```
eth0  10.1.0.7/22          ← 内网地址
default via 10.1.0.1 proto dhcp
公网 106.53.42.186         ← NAT 映射，不在网卡上
```

reinstall 自己的卖点里列了静态 IP、`/32`、网关不在子网范围内这几种麻烦情况——
这里都不是。**镜像里跑一个 DHCP 客户端就能上网**，不需要把地址写死。

### 控制台：`console=ttyS0,115200` 是硬要求

TX 的 cmdline 里有 `console=ttyS0,115200 console=tty0`，串口 getty 在跑，
腾讯云网页 VNC 走的就是它。**镜像内核参数不带这个，第一次启动就是纯黑屏。**

### 内核：virtio 必须内建

`virtio_blk` / `virtio_net`。这一条**已经在 5.5 里了**（「virtio/串口/NVMe 内建」），
不需要改需求。

### 分区：root 别写满

盘是 40G，镜像得留 growpart 的余地。

### 退路：起不来的时候有救援

`reinstall.sh alpine --hold 1` 进内存系统，`/trans.sh alpine` 救砖。
**这正是 TX 适合当第一个目标的原因。**

## 五、TX 的角色

### 现在：真机验证机

环境搭建指南里写着，Docker 做不到的三件事是 `chroot` 进去测试、验证系统能不能
启动、将来构建和测试 ISO——而**这三件事还没有开始做**。TX 就是干这个的机器。

它今天跑的 Rocky Linux 10 **不用动**：那份指南推荐 Ubuntu Server 是给全新机器
选型用的，不是给已经在跑的机器。Rocky 10 的工具链比 Ubuntu 24.04 还新。

### x86_64 这件事有两面

一面是路线图上的：它在 x86_64 那一侧，比 aarch64 产物**晚一整个阶段**
（见待办 §2）。aarch64 的产物对它一行都用不上。

另一面更值得注意：README 的第 2 条要求是「主流国产商业软件可靠运行」，而那些
预编译二进制**绝大多数是 x86_64 的**。所以在 TX 上做 `chroot` 测试，比在 Mac 的
aarch64 上**更贴近真正的验收目标**。

**它不是「排在后面对付一下」的架构，它是要求 2 的目标架构。**

### 将来：第一个 DD 目标

```
1. 用 QEMU 验证 5.5 / 5.6 的产物能启动
2. 做出第一张 .img —— 不一定非得是 x86_64 的
3. x86_64 线（待办 §2）跟上，产出 x86_64 的 .img
4. TX 上：reinstall.sh dd --img <URL>
5. 起不来就 reinstall.sh alpine --hold 1，改完再 DD
```

**TX 是唯一一台坏了不心疼的机器**——reinstall 一条命令就能把它变回任何系统。
所以它当第一个 DD 目标，比任何生产机器都合适。

## 六、镜像怎么产出、放在哪里（2026-10-12 补）

### 产出：`pantsu img`

```
pantsu rootfs <风味> --arch x86_64     ← 从 apk 仓库装出一个根
pantsu img    <风味> --arch x86_64     ← 混合 GPT + 引导器 + grub.cfg → .img.zst
```

**不是 skirt 的新产物类型。** skirt 建包、pantsu 建系统——磁盘镜像属于「系统」
那一侧，所以它在 distro 里，不在 packages 里。这也是两个仓库那条边界的第一次
实际检验：`pantsu img` 只认一个 apk 仓库 URL，不读 `var/output/`。

分区表照腾讯云那套模板抄（实测两次，连文件系统 UUID 都一样）：

```
ESP 512M（fat32，boot/esp）· bios_grub 1M · root（ext4，PARTLABEL=yojigenos-root）
```

**引导器选型：GRUB，两个 target 都装。** `i386-pc`（BIOS）+ `x86_64-efi` /
`arm64-efi`（UEFI，走可移动介质路径 `\EFI\BOOT\BOOTX64.EFI`——DD 不写 NVRAM
启动项，只能靠这个约定）。EFI stub 直接引导内核被否掉了，理由就是下一条。

**单引导还是双引导：双（混合 GPT）。** 2026-10-12 在 TX 上实测：SeaBIOS 把 MBR
全零的 GPT 盘当成"从硬盘启动"，然后停在那里不动——**这台实例没有 UEFI**。既然
BIOS 是真实存在的一半、UEFI 是另一半，代价又只是一个 1 MiB 分区加一套引导器，
那就两个都留。

**已在 QEMU 里真启动验证**（不是看文件对不对）：aarch64 + UEFI 走到了串口问候
（edk2 → GRUB → 我们的内核 → ext4 根 → `/init`）；x86_64 + BIOS 用占位内核验到
「内核被装载并执行」（SeaBIOS → MBR 的 boot.img → bios_grub 的 core.img → 读
ext4 → 装载 bzImage）。把占位内核换成我们自己的，等 x86_64 的包发布。

### 托管：就放在仓库里，和 apk 同一个桶

```
<桶>/<架构>/…                            apk 仓库（apk 自己的约定）
<桶>/img/<风味>/<架构>/<…>.img.zst        交付物，不可变
<桶>/img/<风味>/<架构>/<…>.img.zst.sha256 它的校验值
<桶>/img/<风味>/<架构>/latest.txt         一行文件名
```

于是有两条 URL：

```
https://repo.os.yojigen.cn/img/minimal/x86_64/minimal-x86_64-20261012.img.zst
https://repo.os.yojigen.cn/img/minimal/x86_64/latest.txt
```

**为什么不用腾讯云 COS。** 从 TX 拉 COS 确实走内网（实测 60 MB/s 以上、流量不
计费），但一张 40 MB 的镜像走公网也就是几分钱，而多一条链路就多一个会坏的地方、
多一套要轮换的凭据。**交付物只能有一个出处**——这条规矩在这个项目里已经付过
一次学费（见 README 里「不读 var/output/」那段）。

**为什么是 `latest.txt` 而不是覆盖一个 `latest.img`。** 交付物不可变（文件名带
日期，永不覆盖），而 `dd --img` 又需要一个不用改脚本的固定 URL。一行文本同时
满足两件事：

```sh
IMG=$(curl -s https://repo.os.yojigen.cn/img/minimal/x86_64/latest.txt)
reinstall.sh dd --img https://repo.os.yojigen.cn/img/minimal/x86_64/$IMG
```

发布是 `pantsu img --publish --go`（默认干跑，只列要传什么）：rclone，和
`packages/scripts/deploy.sh` **同一套环境变量**（`S3_AK` / `S3_SK` /
`S3_BASE_URL` / `S3_BUCKET`，CI 里就是同一批组织级 secret）。**只 copy，绝不
sync**——桶是多来源共用的（apk 在 `<架构>/`、镜像在 `img/`），sync 会删掉别人
已经引用的东西。

### 发布清单怎么算出来的（别手写）

`skirt` **不会自动建依赖**——它只会告诉你「依赖 X 还没有构建」。所以要发的包是：

```
variants/<风味>.toml 的全部
  + 这些包的构建依赖里【不在 base-devel 闭包内】的那些
```

第一次发 x86_64（2026-10-12）就撞上了这件事：`linux` 的构建依赖里有
`flex` / `bc` / `openssl`，三个都不在 base-devel 里，于是建到最后一个包才报错
——前面 15 个白建了一遍（20 分钟）。

算的方法（用 `skirt provides`，别猜）：

```sh
cd packages
./skirt/skirt provides $(distro 那边 base.toml 的包) flex bc openssl \
    util-linux yojigenos-init linux
```

2026-10-12 算出来是 **21 个**：base 的 15 个（含 apk-tools / ca-certificates）
+ flex / bc / openssl（`linux` 的构建依赖）+ util-linux / yojigenos-init / linux。

```sh
gh workflow run release.yml -f "packages=<那 21 个>" -f arch=x86_64 -f deploy=true
```

★ `grub` / `openssh` 还没有配方，所以 `minimal` 现在装出来是**故意不完整**的
（`pantsu rootfs --skip-missing` 会连报三次警告）；建盘用的引导器暂时是借
Alpine 的，等 `grub` 配方出来换成 `--directory`。

## 还没定

1. **首次启动的配置怎么注入。** 机制定了：`yojigenos-init`，几十行 shell，
   不用 cloud-init。但 **SSH 公钥怎么进去还没定**——DD 模式没有任何注入点
   （reinstall 不会替我们改盘），所以要么当构建参数（一张镜像带一把公钥），
   要么装机时从 VNC 手敲一遍。
2. **装到大盘上多出来的空间归谁。** 镜像默认 1 GiB，装进 40 GiB 的盘之后剩下
   的没人管（growpart + resize2fs 都在 first-boot 那一侧，还没做）。
3. **要不要 fork reinstall 把自己加进它的菜单。** 它文档里专门有一节讲怎么改
   脚本自用。那等于让别人认识我们，**比 DD 更省事但更依赖对方**。不急。
4. **`x86_64` 的包什么时候发布。** 前置全在 packages 那边（`release.yml`）。
   发布之前，`pantsu img --arch x86_64` 拿不到根。

## 七、2026-10-16：通道第一次真的走通 —— 而它逼出七个缺口

> 注（2026-10-16 追加）：这一节记的是**实测**，不是打算。原文保持原样。

那晚的目标是把 `minimal` 装到 TX 上。**走通了**，而代价是七处只有在真机上
才露出来的缺口。记下来是因为它们有一个共同点：

> **全都在"绿着"的状态下存在过。** 构建绿、测试绿、CI 绿、`pantsu vm` 也起得来。

| # | 缺口 | 症状 | 为什么此前没被发现 |
|---|---|---|---|
| 1 | 没有 `/dev/fd` 那四个符号链接 | `bash` 的进程替换整个不能用 | CI 那条启动验证不跑进程替换；**一晚上咬了两次** |
| 2 | `grep` 没有 `-P` | 脚本 `grep -oP` 直接失败 | **configure 警告过**，而它淹在 87 个包的日志里 |
| 3 | 没有 `reboot` / `poweroff` | 服务器重启不了 | 两边都是别的发行版给的（Alpine 靠 busybox、Debian 靠 systemd），而我们两个都没有 |
| 4 | `grub.cfg` 不读 `custom.cfg` | 一次性引导项被完全无视 | `pantsu vm` 默认 `--mode direct`，**根本不经过 GRUB** |
| 5 | 读了 `custom.cfg` 也还得自己 `load_env` | 那段**安静地跳过自己** | 那是 Ubuntu 系的写法；而"没跑"这件事没有声音 |
| 6 | UEFI 下 `${config_directory}` 指向 memdisk | 同一份 `custom.cfg`，BIOS 读到、UEFI 读不到 | **两个环境都是 BIOS**（CI 用 SeaBIOS、TX 是 BIOS） |
| 7 | `stage()` 不搬 `.buildkey` 边车 | **每轮 CI 全量重建**（87 包 × 2 架构 × ~2h） | 症状是"盘上没有它上次的 build_key"，离成因很远 |

### 1 和 3 的细节值得单说

**`/dev/fd`**：`devtmpfs`（内核自动挂的那个）**只给设备节点**，而
`/dev/fd`、`/dev/stdin` 这些是**指向 `/proc/self/fd` 的符号链接**，得有人建。
Alpine 靠 `mdev`，Debian 靠 `systemd-tmpfiles`，**而我们一个都没有**。
改法是在我们自己的 `/init` 里建 —— 而它咬了两次：第一次手工 `ln -sfn`
建了，重启之后又没了（因为 `/dev` 是 devtmpfs）。

**`reboot`**：`util-linux` **早就不提供** `reboot`/`poweroff`/`shutdown`/`halt` 了
（2.42 的源码里一个都没有；`--disable-kill` 只管 `kill` 那一个程序）。
所以由 `yojigen-os-init` 自己提供，走内核的 sysrq 接口。

### 4、5、6 是同一件事的三层

`reinstall.sh` 那类工具的做法是：把一个一次性引导项写进 `/boot/grub/custom.cfg`。
而它要真的生效，**三个条件缺一不可**：

    ① GRUB 得去读那个文件          （4：要么 source，要么它永远看不见）
    ② 得先把 grubenv 读进来        （5：它那段开头的 `if ! [ -s … ]` 是
                                      给 Ubuntu 系写的，那边 00_header 先 load_env；
                                      我们没有，于是它每次判定"读过了"就跳过）
    ③ 得找得到【盘上】那一份        （6：我们那个 EFI 是 grub-mkstandalone 做的，
                                      配置嵌在文件里，于是配置目录和 prefix
                                      都指向 memdisk；解法是先去 search 根分区）

★ 而"没生效"这件事**本身是安静的**：重启之后回到原系统，日志里一个字都不说。
  判据是 `grubenv` 里的 `next_entry` **还在不在** —— 那段代码跑过就会清掉它，
  还在就说明一次都没跑。

### 7：一处漏搬、全域失效

    pack     写  var/pkgs/<名>.apk  +  <名>.apk.buildkey      ✓
    stage    只搬 <名>.apk                                     ✗ ← 漏在这儿
    deploy   把 var/repo/ 传上去（除索引外的一切）
    restore  按 <名>.apk.buildkey 找上次的 key → 找不到
             →「盘上没有它上次的 build_key」→ 全量重建

而 `pack.py` 里那个函数的 docstring **早就写下了这个危险**
（"没有这份……于是每次都重建，build_key 那个机制就白做了"）——
**它写对了，只是隔壁另一个模块没跟上。**

### 而"临时环境起不来"那一次

那晚 TX 掉进过一次 Alpine 的 initramfs 应急 shell，屏幕上是：

    Installing packages to root filesystem…
        WARNING: … DNS: transient error (try again later)
    OK: 0 B in 0 packages
    /init: line 116: can't open /dev/fd/64: no such file
    /sbin/init not found in new root
    Launching initramfs emergency recovery shell.
    ~ #

**DNS 不通 → `modloop`/`apk` 下不来 → 新根里没有 init → 掉进应急 shell。**

★ 而它是**活的**（有一个 shell 在等），不是砖。**出路是敲 `reboot`** ——
  因为 `grubenv` 里的 `next_entry` 已经被消费掉了（第 5 条那段跑过就清），
  所以 GRUB 下次会选回 "Yojigen OS"，回到装好的系统。

★ 而那句 `can't open /dev/fd/64` **Alpine 自己的 initramfs 里也有** ——
  也就是说它能忍受，**不是**它掉进 shell 的原因。这一条别误判。

### 共同的形状

七条里有六条的"没被发现"是同一个理由：**验证走的那条路，和真机走的那条路，
不是同一条。** `pantsu vm` 用 `--mode direct` 绕过 GRUB；CI 用 SeaBIOS；
CI 不跑进程替换；CI 不重启机器。

**所以这一节的结论不是"下次仔细点"**，而是：**"真装一次"本身是一道测试**，
而它该有自己的一条路 —— 见 `docs/指南/安装到真机.md`。
