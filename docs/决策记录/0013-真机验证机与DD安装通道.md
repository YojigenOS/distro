# 0013 真机验证机与 DD 安装通道

- **日期**：2026-10-10
- **状态**：**已决定**（磁盘镜像的产出方式待定）
- **影响范围**：交付形式模型（0007）、`skirt` 的产物类型、将来的镜像构建、真机验证机（TX）的用途

## 背景

一台服务器到手了（腾讯云 CVM，SSH 别名 `TX`）。问题是：**怎么把我们自己的系统装上去？**

自然的想法是找现成的重装脚本，比如 <https://github.com/bin456789/reinstall>。
它确实能用，但它的五个功能里**只有一个**能接自建发行版。而搞清楚是哪一个，
顺手把几件悬着的事定了。

## 一、那类工具不是安装器

| 功能 | 命令 | 对我们的意义 |
|---|---|---|
| 重装到 20 种常见发行版 | `reinstall.sh debian 13` | ❌ 它认识的是别人家的镜像源 |
| **DD RAW 镜像到硬盘** | `reinstall.sh dd --img URL` | ✅ **唯一入口** |
| 引导到 Alpine Live OS | `reinstall.sh alpine --hold 1` | 🔧 救援与手动操作 |
| 引导到 netboot.xyz | `reinstall.sh netboot.xyz` | 🔧 同上 |
| 装 Windows ISO | `reinstall.sh windows` | ❌ |

它的工作方式是**先把自己引导进一个临时的 Linux 内存环境，再从那里装系统或写盘**。
所以它不是安装器，是「**引导 + 写盘**」。

功能 1 之所以能装 20 种系统，是因为它内置了那 20 种系统的无人值守流程——
对我们这种它没听说过的系统，这条路不存在。

**DD 那条路支持什么：**

```
raw 和固定大小的 vhd
未压缩，或压缩成 .gz .xz .zst .tar .tar.gz .tar.xz .tar.zst
```

正好是发布附件的形状（0007 已经定了可启动产物进 Releases）。

**最要紧的一句话在它的文档里：**

> DD Linux 镜像时，**不会**修改镜像的任何内容。

对 DD Windows 它会自动扩展系统盘，静态 IP 的机器还会配好 IP；对 Linux
**什么都不做**。这句话决定了后面所有的设计——**镜像得自己带一切。**

有一个例外接口：`--cloud-data`，可以给 DD 的 Linux 镜像注入 cloud-init 的
NoCloud 配置（`user-data` 必需，`meta-data` / `network-config` 可选）。但那是
**外部的可选注入**，不能当作我们的配置机制。

两条备用路径：`--hold 1` 只重启到安装环境不安装（先验证网络），`--hold 2`
DD 完不重启（SSH 进去改）。救砖则是进环境后跑 `/trans.sh alpine`。

> ⚠️ 它不支持 OpenVZ / LXC 容器型 VPS。TX 是 KVM，不在这个限制里。

## 二、决定：磁盘镜像是独立的交付形式

**0007 待定项 #4 的答案：该分开。**

0007 开头列了四种形式（容器 / ISO / 磁盘 / 内核），但下面的矩阵只画了两列。
**本记录填的是「磁盘」这一格。**

分开的理由**不是格式，是消费方式**：

| | ISO | `.img` |
|---|---|---|
| 分区表 | 不需要 | 必须有 |
| 引导器写在哪 | 挂载方决定 | 构建时写死 |
| 里面是什么 | 只读压缩 + 可写层 | 解开就是系统本身 |
| 首次启动配置 | 安装器负责 | 镜像自己负责 |
| **谁能用** | 有 IPMI / VNC / U 盘的人 | **只有 SSH 的人** |

最后一行是决定性的。**`.img` 是唯一一种对方不需要认识我们的形式。**

netboot / kexec 那条路技术上也能无人值守——reinstall 的功能 3 就是——但它要求
**对方的引导器里得有我们这一项**，而 reinstall 的菜单里只有那 20 种。DD 不同：
它是一次通用的「把这些字节写进硬盘」，**不需要任何人的配合**。

## 三、决定：VPS 这条路径上，我们不写安装器

README 的「现在不要做的事」里写着**安装器**。这条决定把它从清单里划掉：

**不是推迟，是取消**——至少在 VPS / 服务器这条路径上。

代价换成了一条义务：**产出 `.img`，并且它自带一切。** 引导链、内核、`/init`、
首次启动配置，Docker 里能跑通的东西一样都不能少。

（真机从 U 盘装、要人参与选分区的那种安装器是另一件事，这里没有取消它。
但它也不是现在的事。）

## 四、实测出来的约束

下面每一条都是从 TX 上量出来的，不是推测。实现 `.img` 的时候直接照这个来。

```
x86_64   Xeon Platinum 8255C @ 2.50GHz   4 vCPU
3.6 GiB 内存        40 GiB 盘（vda，virtio-blk）
Rocky Linux 10.2    kernel 6.12          腾讯云 CVM，KVM
```

### 引导：BIOS + GPT，而模板留了双引导的位置

```
vda1   512M   EFI System      ← 存在，但没被使用
vda2     1M   BIOS boot       ← 现在走的是这个
vda3  39.5G   Linux root      ← xfs
```

`/sys/firmware/efi` 不存在，所以是 SeaBIOS 引导；1M 的 `vda2` 正是 GPT 下
grub-pc 需要的 `bios_grub` 分区。而 ESP 也在——**腾讯云这套模板是双引导布局。**

因为 DD 一个字节都不改，**镜像自己的分区表就是最终分区表**。所以我们的 `.img`
也应该做成混合 GPT（`bios_grub` + ESP 都在），否则换一台同商家的实例可能起不来。

### 网络：NAT 内网 + DHCP，不用硬编码

```
eth0  10.1.0.7/22          ← 内网地址
default via 10.1.0.1 proto dhcp
公网 106.53.42.186         ← NAT 映射，不在网卡上
```

reinstall 自己的卖点里列了静态 IP、`/32`、网关不在子网范围内这几种麻烦情况——
这里都不是。**镜像里跑一个 DHCP 客户端就能上网**，不需要把地址写死。

### 控制台：`console=ttyS0,115200` 是硬要求

TX 的 cmdline 里有 `console=ttyS0,115200 console=tty0`，串口 getty 在跑，
腾讯云网页 VNC 走的就是它。**镜像内核参数不带这个，第一次启动就是纯黑屏。**

### 内核：virtio 必须内建

`virtio_blk` / `virtio_net`。这一条**已经在 5.5 里了**（「virtio/串口/NVMe 内建」），
不需要改需求。

### 分区：root 别写满

盘是 40G，镜像得留 growpart 的余地。

### 退路：起不来的时候有救援

`reinstall.sh alpine --hold 1` 进内存系统，`/trans.sh alpine` 救砖。
**这正是 TX 适合当第一个目标的原因。**

## 五、TX 的角色

### 现在：真机验证机

环境搭建指南里写着，Docker 做不到的三件事是 `chroot` 进去测试、验证系统能不能
启动、将来构建和测试 ISO——而**这三件事还没有开始做**。TX 就是干这个的机器。

它今天跑的 Rocky Linux 10 **不用动**：那份指南推荐 Ubuntu Server 是给全新机器
选型用的，不是给已经在跑的机器。Rocky 10 的工具链比 Ubuntu 24.04 还新。

### x86_64 这件事有两面

一面是路线图上的：它在 x86_64 那一侧，比 aarch64 产物**晚一整个阶段**
（见待办 §2）。aarch64 的产物对它一行都用不上。

另一面更值得注意：README 的第 2 条要求是「主流国产商业软件可靠运行」，而那些
预编译二进制**绝大多数是 x86_64 的**。所以在 TX 上做 `chroot` 测试，比在 Mac 的
aarch64 上**更贴近真正的验收目标**。

**它不是「排在后面对付一下」的架构，它是要求 2 的目标架构。**

### 将来：第一个 DD 目标

```
1. 用 QEMU 验证 5.5 / 5.6 的产物能启动
2. 做出第一张 .img —— 不一定非得是 x86_64 的
3. x86_64 线（待办 §2）跟上，产出 x86_64 的 .img
4. TX 上：reinstall.sh dd --img <URL>
5. 起不来就 reinstall.sh alpine --hold 1，改完再 DD
```

**TX 是唯一一台坏了不心疼的机器**——reinstall 一条命令就能把它变回任何系统。
所以它当第一个 DD 目标，比任何生产机器都合适。

## 还没定

1. **`.img` 怎么产出。** 分区表、文件系统、引导器安装、growpart、first-boot
   机制，全没设计。`skirt` 要不要多一种产物类型，也没想。
2. **首次启动配置用什么。** cloud-init 最现成，但它拖进一整套 Python——和
   「精简、轻巧」有张力，而且这条依赖链落在 5.8 的 apk 那条线上。
   **一个几十行的 shell 脚本可能就够了。** 没定。
3. **单引导还是双引导。** 混合 GPT 两头都能起，代价是多一个分区和一套引导器。
4. **引导器选型。** GRUB / systemd-boot / EFI stub 直接引导内核——这是
   0007 待定项 #3，**本记录没有回答它**。
5. **要不要 fork reinstall 把自己加进它的菜单。** 它文档里专门有一节讲怎么改
   脚本自用。那等于让别人认识我们，**比 DD 更省事但更依赖对方**。不急。
6. **`.img` 的命名与版本号。** 0007 待定项 #5 仍然开着。
7. **什么时候做。** 前置全在 5.5 / 5.6 之后。**这不是现在的事。**
