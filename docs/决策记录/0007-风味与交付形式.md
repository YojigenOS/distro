# 0007 风味与交付形式

- **日期**：2026-10-10
- **状态**：⚠️ **草案 —— 方向大致清楚，细节未定稿**
- **影响范围**：风味机制的实现、`skirt rootfs` 的命令行、产物的命名与分发位置

> **这份记录和别的决策记录不一样，它不是定论。** 讨论时说的是「也许大概是这个
> 意思」，所以下面区分了「比较确定的」和「还没想清楚的」。等真正实现风味机制
> 时再定稿。

## 背景

决策记录 0003 定了镜像命名——**仓库名放变体、tag 放版本**：

```
yojigenos/base          最小运行时
yojigenos/base-devel    base + 工具链
yojigenos/desktop       base + 桌面
```

那份记录里的「变体」和现在说的「风味」是同一件事。

但它只考虑了**容器镜像**这一种产物。而当 `minimal` 的定位变成「既能取代 Alpine
当容器、又能启动成一台机器」之后，问题暴露出来了：

**一个风味可以有多种交付形式，而不同形式需要的包不一样。**

```
minimal 容器版  →  不需要内核（宿主提供）
minimal ISO 版  →  必须有内核和完整引导链
```

**同一个风味，两套包。** 0003 的单一命名放不下这件事。

## 比较确定的：两个维度

```
风味（flavor）     =  一组包 + 一个用途        ← 用什么
交付形式（format） =  容器 / ISO / 磁盘 / 内核   ← 怎么给
```

**我早先的设计是错的**：当时想在风味文件里写 `kind = "container" | "bootable"`，
那等于假设一个风味只有一种形式。

### 不是自由组合——有些格子是空的

| 风味 | 容器镜像 | ISO / 可启动 |
|---|---|---|
| `base` | ✅ 就是这个用途 | ❌ 不能启动的东西做成 ISO 干嘛 |
| `base-devel` | ✅ 构建环境 | ⚠️ 工具链 ISO，很少见 |
| **`minimal`** | ✅ 取代 Alpine | ✅ 救援系统 |
| `server` | ⚠️ 少见 | ✅ 主用途 |
| `desktop` | ⚠️ | ✅ 主用途 |

**`minimal` 两格都占**，这正是它的价值：同一套用户态，既能 `docker run`，
也能启动成一台机器（Alpine 就是这样）。

## 比较确定的：产物命名分两条路

| 形式 | 去哪 | 长什么样 |
|---|---|---|
| 容器镜像 | 镜像仓库 | `yojigenos/minimal:edge`（沿用 0003） |
| 可启动镜像 | 发布附件 | `yojigenos-minimal-2026.10.10-aarch64.iso` |
| 内核 + initramfs | 发布附件 | `yojigenos-minimal-…-Image` + `-initramfs.cpio.gz` |

**OCI 镜像进 registry，ISO 进 Releases**——两条分发路径本来就不一样。

## 还没想清楚的

### 1. 风味文件的结构（草案，未验证）

```toml
# variants/minimal.toml —— 用户态，两种形式共享
[variant]
name        = "minimal"
description = "最小系统：能启动、能联网、能装软件"
packages    = ["filesystem", "glibc", "bash", "coreutils", …,
               "openssl", "curl", "ca-certificates", "apk-tools"]

[variant.formats.container]
exclude = ["linux"]                  # 容器不需要内核

[variant.formats.iso]
include = ["linux", "initramfs", "grub"]
```

**不确定**：`exclude` / `include` 这种增量写法对不对？还是干脆每个形式写一个
完整列表更清楚（重复但直白）？**没有真实需求之前不写代码。**

### 2. `base` 和 `minimal` 是什么关系

- 独立定义（两个包列表，可能重复）
- 还是包含关系（`base` ⊂ `minimal`，后者多 apk 那一串）

**不确定**。倾向包含，但要看风味多了之后哪种更好维护。

### 3. ISO 怎么引导

GRUB？systemd-boot？EFI stub 直接引导内核？**没想**。这取决于内核 config 和
是否要支持老机器。

### 4. 「磁盘镜像」算不算一种形式 —— **已定：算，独立一格**

给 VPS 和真机装系统用的是磁盘镜像（`.img`），它和 ISO 的需求不同
（分区表、文件系统、first-boot 配置）。**现在归在"可启动"这一格里，但可能该分开。**

**已定：该分开。** 理由不是格式，是**消费方式**——ISO 需要有人把它挂上去
（IPMI、VNC、U 盘），`.img` 只需要被写进硬盘。**它是唯一一种对方不需要认识
我们的形式。**

论证、实测约束和安装通道见**决策记录 0013**。

### 5. 可启动产物的版本号

容器镜像有 tag（`:edge` / `:2026.10.10`）✓ 那 ISO 呢？

- 用同样的日期？✓ 简单
- 还是等真发布时才有版本号？

**不确定。** 而且这和 `os-release` 里 `VERSION` / `VERSION_ID` 空着那件事是同一个
问题（见决策记录 0005 的讨论——因为构建频繁，暂时不设）。

## 什么时候定稿

**实现风味机制的时候。** 在那之前：

- `base` 只占一格（容器），所以它简单，仍然第一个做
- `minimal` 的两个格子有先后，但**互不阻塞**：
  - 容器版依赖 apk-tools 那一串（perl → openssl → curl → ca-certificates）
  - ISO 版依赖内核 + 引导链
