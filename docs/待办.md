## A1 `pantsu rootfs` 在 macOS 上会丢文件（宿主文件系统，不是我们的代码）

**2026-10-20 实测。** `pantsu rootfs minimal --arch x86_64` 在打包那一步死：

```
tar: ./usr/share/terminfo/2/2621A: File removed before we read it
tar: ./usr/share/terminfo/E/Eterm:  File removed before we read it
…（一批，全在 usr/share/terminfo/）
pantsu: 错误 装根失败（退出码 1）
```

### 判据

| 跑法 | 结果 |
|---|---|
| `pantsu rootfs`（`/newroot` = **宿主绑定挂载**） | 死，报一批 `File removed before we read it` |
| 同一条 `tar` 命令，在**容器的本地目录**里 | **零错误**，145 MB、退出码 0 |
| 装完之后看宿主上那个根 | `usr/share/terminfo/2/2621A` **不存在** |
| CI（Linux）走同一条路 | 好的（`release.yml` 成功过 3 次） |

★★ **所以根因是：`/newroot` 是宿主挂载，13k 个小文件先被 apk 写到宿主文件系统
上，tar 再从同一个挂载读回来 —— 而 macOS 上的 Docker Desktop（VirtioFS）
在这条路上会丢文件。**

### 而它为什么值得记

它是"装上了"和"装对了"的又一例：`apk` 报成功（65 个包）、清单写出来了、
tar 打了 145 MB —— 只有对着 `tar` 的警告才看得出**那个根不完整**。

★ 而它差点被我当成"我们的代码有 bug"。差别在**同一条命令换个文件系统**。

### 现在做了什么

`root.py` 里把那个错误变成一句能行动的话（识别 `File removed before we read
it`，说明成因、指向 Linux / CI）。**没有猜着改架构** —— 因为 Linux 上那条路
是对的。

### 根上的修法（没做）

`/newroot` 不该是宿主挂载。正确的形状：

    在【容器的本地目录】里装 + 打 tar（13k 个文件不经过任何挂载）
    → 只把 /out 挂出去（一个 .tar.gz，一个文件，不会丢）
    → 而 var/<风味>/rootfs-<架构>/ 那棵树改成【从 tar 解出来】的派生品

★ 而它要动 `img.py`（第 423 行读那棵树，要 `cp -a` / `chroot` / bind mount），
所以不是一行的事。

#### 而那个先决条件已经有答案了（2026-10-20 查的）

问：那棵树到底是不是交付物？

**不是。它是中间物。** 判据有三条：

| 判据 | 结果 |
|---|---|
| 谁读 `var/<风味>/rootfs-<架构>/` | 只有 `img.py:423` 和 `vm.py:215` —— 都是"拿它当输入再建别的" |
| 它在 git 里吗 | 不在（`distro/.gitignore` 第 2 行 `/var/`） |
| `pantsu rootfs` 报的产物是什么 | `完成 …/minimal-x86_64.tar.gz` 和 `根 …/rootfs-x86_64/（给后面的步骤当输入）` |

★★ 所以那条修法（在容器本地目录里装 + 打 tar，那棵树改成从 tar 解出来的派生品）
**方向上没有争议** —— 剩下的只是"从 tar 解出来会不会也在宿主上丢文件"这个实测问题，
而那只要跑一次就知道。

## ★ 2026-10-12：用 apk 装 base，抓到一个真实的依赖缺失

装了 base 的 13 个包（175 个命令都在），一跑管道就炸：

    gawk: error while loading shared libraries: libmpfr.so.6: cannot open shared object file

查过了：

    gawk 二进制 NEEDED:   libmpfr.so.6 · libgmp.so.10 · libm.so.6 · libc.so.6
    gawk 声明的 depends:  ['glibc']                       ← 少了两个 ✗

    libmpfr.so.6  →  mpfr-4.2.2-1 包
    libgmp.so.10  →  gmp-6.3.0-1 包
    ★ 这两个都不在 base 的 13 个里

**两道都错了**：配方少声明了依赖，风味少列了运行时需要的包。

**而更重要的是「为什么以前没发现」**：

    直接叠 payload   →  所有 payload 叠在一起，什么库都在 → 不暴露 ✗
    用 apk 装        →  严格按声明的依赖装 → ★ 装完立刻炸 ✓

**「用包管理器装」是一道新的检查**——它把「依赖声明不全」从「运行时偶尔炸」
变成「装完立刻炸」。后者能修，前者查不到。

packages 侧的待办里记着两条审计：「25 个包未声明 gawk 依赖」「12 条未声明的
运行时依赖」。现在它们从"审计发现的清单"变成了"装完就报错的清单"。
