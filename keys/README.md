# 签名公钥

这里放的是**会烤进交付物的公钥**。apk 在装包时用它们验证签名。

组装时 `pantsu rootfs`（`pantsu assemble` 的第一步就是它）会把这里的每一个
`*.rsa.pub` 复制到交付物的 `/etc/apk/keys/` 里——**在装第一个包之前**，因为
装第一个包时就要验签，而验签要公钥。这也是「信任从哪里开始」的答案：公钥来自
交付物自己的构建输入（这个目录，在 git 里），不经过网络，不依赖 HTTPS 锚定。

## 命名

```
<身份>-<生成时间戳的十六进制>.rsa.pub

os@yojigen.cn-6acc475d.rsa.pub
              └─ 0x6acc475d = 生成时间
```

和 Alpine 的形状一致（`alpine-devel@lists.alpinelinux.org-58199dcc.rsa.pub`，
那个 `58199dcc` 是 2016-11-02）。

两处和 Alpine 不同，都是有意的：

- **没有用邮箱当身份。** Alpine 用的是真实的邮件列表，那套的精髓是
  「身份是个能联系上的地址」。我们没有一个 `os@yojigen.cn` 的签名邮箱，
  写上去就是假的——学形式丢掉精髓不如不学。所以这里用的是域名的邮箱形式，
  它至少指向一个我们控制的域名。
- **名字里不写用途。** 三把是**等价的**：任何一个都能签、都能顶上。
  谁当「备用」是会变的，写进名字反而在撒谎。

`apk` 完全不关心这个名字（只要以 `.rsa.pub` 结尾）。所以它纯粹是给人看的。

## 三把密钥在哪

| 名字 | SHA256 指纹 | 存哪 |
| --- | --- | --- |
| `os@yojigen.cn-6acc475d` | `7c7ee14c9a08bad77cc8ffad4947947b` | ★ GitHub org secret `SIGNING_KEY` |
| `os@yojigen.cn-6acc475e` | `a59915f23b144662e8900743d3cdb554` | 待定（密码管理器） |
| `os@yojigen.cn-6acc475f` | `6ff18f51f327ebdd9a1f05cb7cc82559` | 待定（异地） |

**私钥在 `~/.yojigenos/keys/`，不在任何仓库里。**

### ★ secret 不是备份

GitHub secret 存进去就读不出来了。所以**进了 secret 的那把也要另外备份**。
三把都要有独立的、至少两份的备份——因为「全部丢失」和「某个泄露」是两种
不同的灾难，而备份份数解决的是前者。

## 为什么是三把，不是九把

考虑过九把，但那个方向是错的：

```
N 把密钥 → 「全部丢失」的概率下降   ✓（这是想优化的）
         → 「至少一个泄露」的概率上升 ✗（而这个更严重）
```

丢掉全部：无法签新包，但**已经装好的系统仍然是安全的**。
泄露一把：攻击者能签出**看起来完全合法**的恶意包，已装系统会信任地装上。

而九把私钥就是九个要保管的东西。如果只认真保管其中三把，那和只做三把
一样安全，却多出六把「可能被随手放着」的私钥——每一把都能签出合法包。

三把够用：任意一把在手就能签，丢两把还剩一把，泄露一把还能用另外两把
发一次「撤销那次更新」。

## 为什么是 RSA，不是 ed25519

实测过（apk-tools 3.0.8）：

```
ed25519   ✗ Failed to load signing key: crypto error
ECDSA     ✓ 能签
RSA       ✓ 能签
```

**ed25519 本该是最合适的**——它和 RSA 一样是确定性的（签名不带随机数），
而且更快、密钥更短。但 apk 没实现它。

**ECDSA 能用但不能用**：它的签名带随机 nonce，同一个包签两次字节不同，
直接破坏 0005（可复现构建）。实测：

```
RSA     两次签出来完全一样   2dbccc7a… = 2dbccc7a…
ECDSA   两次不一样           22221984… ≠ f5a1be0c…
```

所以 RSA 2048 是唯一同时满足「apk 支持」和「确定性」的选择。

## 轮换

apk 的信任模型是**平权**的：`/etc/apk/keys/` 里所有 `.rsa.pub` 都算数，
没有根密钥、没有密钥链、没有主从。所以：

- **加**一把新密钥很容易——放进来，随下次镜像更新分发出去
- **去掉**一把已经发出去的密钥极难——得让所有已装系统更新它们的
  `/etc/apk/keys/`，而那个更新本身也得用还能信任的密钥签

**所以「多放几把」要在一开始做。** 一旦发布出去，公钥就固化在别人的系统
里了，那时只能加、不能换。

## 相关

- 生成和检查：`packages/scripts/keys.sh`（`gen` / `show` / `check`）
- 用它签名：`packages/scripts/pack.sh --sign-key` 和 `repo.sh --sign-key`
- 用它验签：`pantsu rootfs` / `pantsu assemble` / `pantsu img`（自动读这个目录）
